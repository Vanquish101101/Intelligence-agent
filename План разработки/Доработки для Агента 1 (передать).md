# Доработки для Агента 1 (Intelligence agent) — нужны Агенту 3

Этот файл не для разработки здесь — он для передачи в проект `Intelligence agent`
(папка `Marketing agency Project/Intelligence agent`). Ниже описано, чего сейчас не хватает
в выводе Агента 1, чтобы Агент 3 мог полноценно анализировать его данные, а не только готовый
Telegram-текст.

## Текущее состояние

Оркестратор Агента 1 (`Code/src/orchestrator/index.js`) сейчас возвращает:

- `report` — **готовую отформатированную markdown-строку для Telegram** (эмодзи-заголовки,
  `*bold*`, секции 🔥 Топ-тренды / 📱 По платформам / 💡 Идеи для контента / ⚠️ Проверить)
- `meta` — `tools_used`, `errors`, `duration_sec`, `cost_usd`, `cost_breakdown`, `depth`,
  `model_used`

При этом внутри Scout-агента (`Code/src/agents/scout/index.js`) до генерации текста существуют
**сырые структурированные данные**, которые собираются из трёх источников параллельно
(`Promise.allSettled`):

- `scoutResult.data.perplexity` — `{ summary, citations }`
- `scoutResult.data['apify-youtube']` — массив `{ title, views, likes, url, channel, description }`
- `scoutResult.data.firecrawl` — массив `{ title, url, content }`

Эти данные сейчас **схлопываются в текст LLM-промптом и никуда дальше не экспортируются** —
после генерации Telegram-отчёта они теряются.

## Почему это проблема для Агента 3

Агент 3 получает и анализирует данные — ему нужна структура (что за источник, какие цифры,
какие цитаты, какие ссылки), а не уже готовый человекочитаемый текст, из которого пришлось бы
заново вытаскивать факты обратным парсингом. Разбор markdown-текста ненадёжен (эмодзи/форматирование
может меняться) и теряет часть исходных данных (например, `views`/`likes` у видео или список
`citations` Perplexity в тексте могут быть не показаны дословно).

## Что нужно доделать

1. **Не выбрасывать сырые данные Scout-агента.** Помимо готового Telegram-текста, оркестратор
   должен отдавать (возвращать из функции / сохранять в БД) структурированный JSON с тем, что уже
   и так собрано: `perplexity.summary`, `perplexity.citations`, список видео от `apify-youtube`
   (с `title/views/likes/url/channel/description`), список страниц от `firecrawl`
   (`title/url/content`).

2. **Реализовать целевой формат отчёта**, уже описанный в `05. Архитектура.md` §9.2 этого же
   проекта (Агент 1), но пока не реализованный в коде:
   ```json
   {
     "task_id": "uuid",
     "status": "ok | partial | error",
     "report": {
       "trends": [...],
       "by_platform": {...},
       "content_ideas": [...],
       "alerts": [...]
     },
     "meta": { "tools_used": [...], "duration_sec": .., "cost_usd": .. }
   }
   ```
   Сейчас `report` — это строка, а не объект с `trends/by_platform/content_ideas/alerts`. Нужно,
   чтобы LLM (или отдельный шаг после LLM) формировал именно эту структуру, а Telegram-текст
   генерировался из неё как производный формат для бота, а не единственный результат.

3. **Привести формат к общему контракту цепочки.** Агент 2 уже возвращает данные в виде
   `{ job_id, content_type, result, confidence: { level, explanation }, meta }` — с явной меткой
   уверенности в качестве данных. Чтобы Агент 3 обрабатывал вход от Агента 1 и Агента 2 одним
   общим кодом, стоит обернуть отчёт Агента 1 в такую же обёртку, например:
   ```json
   {
     "job_id": "uuid",
     "source_type": "search",
     "result": { "trends": [...], "by_platform": {...}, "content_ideas": [...], "alerts": [...],
                 "raw": { "perplexity": {...}, "youtube": [...], "firecrawl": [...] } },
     "confidence": { "level": "высокая|средняя|низкая", "explanation": "..." },
     "meta": { "tools_used": [...], "duration_sec": .., "cost_usd": .. }
   }
   ```

4. **Дать Агенту 3 способ получить эти данные.** В ТЗ Агента 1 (`04. ТЗ.md` §7.2) и архитектуре
   (`05. Архитектура.md` §12.2) уже запланирован, но не реализован MCP-интерфейс:
   `intelligence.search()`, `intelligence.trends()`, `intelligence.analyze()`, `intelligence.status()`.
   Реализация этого интерфейса (или хотя бы записи структурированного JSON в Supabase, схема
   `intelligence_agent`, в отдельную таблицу типа `search_results`) даст Агенту 3 официальный способ
   забирать данные, вместо разбора Telegram-сообщений.

## Что можно не трогать

Сам Telegram-бот и текстовый отчёт для пользователя менять не нужно — он продолжает работать как
есть. Речь только о том, чтобы **дополнительно** сохранять/отдавать структурированные данные,
которые и так уже собираются внутри Scout-агента, но сейчас нигде не остаются в машиночитаемом виде.

## Пока это не сделано

Агент 3 будет учиться разбирать уже готовый Telegram-текст от Агента 1 как временное решение
(см. `План разработки/1. Идея.md`, раздел «Откуда берётся вход»), и перейдёт на структурированный
вход, когда доработка выше будет готова.
